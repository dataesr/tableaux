# Board development guidance

- Read `client/src/boards/template/routes.tsx` and the relevant files under `client/src/boards/template/` before creating a board. Also inspect one existing board with similar pages or charts. The template is the **design reference** of every board — footer, skip links, page structure, filter bar: follow it; do not copy it blindly, and do not diverge from it (own layout, own component set) without a design decision validated by the team. The header, skiplinks, `<main>` and footer come from `Layout` (`client/src/layout/layout.tsx`, Victor's pull request #201): the board's layout is a thin wrapper around `Layout` that passes `items` (Accueil first, icon `home-4-line`), `serviceTag` / `serviceName`, `footer`, and when needed `before`, `extra`, `navExtra`, `exploreLink`, `languageSelector`, `themeSwitch` — never a board-specific header, navigation bar, `<main>`, `<SwitchTheme />` or skiplinks. The header and navigation are **identical in every board**; a header option is on for all boards or for none.
- Keep board code under `client/src/boards/<board-id>/`. Follow local conventions for `routes.tsx`, page/layout components, `components/`, `pages/`, `styles.scss`, and `i18n` JSON where applicable.
- Use React + TypeScript and the versions already installed in the npm workspace. Prefer existing DSFR, shared components, chart wrappers, hooks, and utilities over new packages or bespoke equivalents.
- For DSFR markup, accessibility, and styling, follow `plugins/tableaux/skills/dsfr/SKILL.md`; inspect actual component types and nearby usage instead of guessing props. A board never rebuilds a component that `@dataesr/dsfr-plus` provides, and its SCSS is layout-only (no colors, borders, shadows, typography or interaction states): see the "UI, DSFR and accessibility" section of the root `AGENTS.md`. A defective shared component is fixed at the source, not replaced locally.
- Accessibility is RGAA-complete and every finding is blocking: write with the checklist in `plugins/tableaux/skills/dashboard/reference/accessibility.md`, not only at review time.
- For Highcharts visualizations, follow the `european-projects` chart layout (`index.tsx`, `query.tsx` or the board `api/`, `options.tsx`, `utils.tsx`; see the `chart` skill in `plugins/tableaux/skills/chart/`) and inspect `client/src/components/chart-wrapper/index.tsx`. Pass the wrapper's `config` and `options`; `options` always comes from `createChartOptions(type, options)` in `client/src/components/chart-wrapper/default-options.ts`. Use existing skeletons and chart-color hooks where suitable, and the data table: `ChartWrapper` shows Highcharts' native table by default; provide `renderData` only when that native table is not readable as is (keys that are not labels, values to format, several axes). Skeleton on first load only; afterwards keep the previous content and grey it out during the API call and during the redraw (see the next rule).
- Grey out every chart, KPI card and data table as soon as it is recomputed (API call pending or re-render in progress), with an overlay, a loading indicator and `aria-busy`; the controls stay usable and show the requested value immediately. Wrap each block that depends on a query in the board's busy overlay with `busy={isPlaceholderData || busy}`, where `busy` comes from the render-transition hook. Reference: `client/src/boards/suivi-recherche/components/chart-busy/` (overlay) and `client/src/boards/suivi-recherche/hooks/use-render-transition.ts` (applies a new value only after the overlay is painted).
- Charts receive chart-ready data. Do not aggregate, rank, sort, join or compute ratios in the browser: add or extend the board's server route instead (see `server/src/routes/boards/AGENTS.md`). Client code limits itself to mapping fields to series, formatting and i18n, memoized with `useMemo` when it depends on a local control. Switching an indicator or tab must not trigger a heavy recomputation.
- Page state that a user can bookmark or share (selected tab, structure, period, filters) lives in URL parameters named after `plugins/tableaux/reference/url-parameters.md`: tabs in `section` (pages are paths), structures in `paysage_id` / `ror_id`, periods in `year` or `year_min` / `year_max`; defaults are not written to the URL and invalid values fall back to them. Reference: `client/src/boards/suivi-recherche/hooks/use-selection.ts` and `pages/bibliometrie/sections.ts`.
- Keep data access out of presentational components where practical. A board's charts call only its own server routes (`${VITE_APP_SERVER_URL}/<board-id>/...`); do not call `/elasticsearch` or other data services from the browser, and do not import fixtures into the client. Follow the closest existing board's query pattern and check response status and loading, error, and empty states rather than assuming a successful JSON response.
- Prototype with synthetic fixture data by default, served by the board's server routes. Do not copy live query payloads or production endpoints from example charts without explicit data-owner approval. Never put service credentials in client code.
- Wire the board into every cross-cutting perimeter: shared `Footer` from `client/src/components/footer` (never a board-specific footer), `sitemap-config.ts` exporting `SITEMAP: BoardSitemapConfig` (site map page and footer), a `plan-du-site` route redirecting to `/plan-du-site?from=<board-id>`, page titles via `title-i18n.json` + `useTitle`, skip links and landmarks as in `template`. Check that the contact form (`/contact?from=<board-id>`) and the accessibility statement (`/accessibility?from=<board-id>`, audit `tableaux_<board-id>`) resolve the board; if they do not, say what is missing (MongoDB record, audit record) instead of leaving dead links.
- Do not assume a board folder is private or published automatically. A production dashboard needs a MongoDB `boards` record with the matching `id`; its route is dynamically imported using that id. Do not create or change that record as part of a prototype unless explicitly requested and approved.
- Every board has a matching server router (`server/src/routes/boards/<board-id>/`) mounted in `server/src/router.js`; follow `server/src/routes/boards/AGENTS.md` and keep the response shape stable as the data source changes.
- If exposing an individual chart through the iframe integration surface, follow `client/src/boards/integration/README.md` and add it to `charts-registry.tsx` only when explicitly requested.
- Run the checks documented in the root `AGENTS.md` and report any test coverage or checks that are unavailable.
