# Repository guidance

## Project structure

- The application is an npm workspace. Use Node.js 24; do not introduce pnpm-only commands.
- The frontend is React + TypeScript + Vite in `client/`; the backend is Express in `server/`.
- Boards live in `client/src/boards/<board-id>/`. Read the board-specific guidance in `client/src/boards/AGENTS.md` before changing a board.
- Board records are stored in MongoDB and returned by `/admin/list-dashboards`. The frontend dynamically imports a board's `routes.tsx` using its record id. Creating a folder alone does not publish a board.
- **A board is wired into every cross-cutting perimeter of the application, not only its own pages.** It uses the shared `Footer` (`client/src/components/footer`), which builds the `/plan-du-site`, `/contact` and `/accessibility` links with `?from=<board-id>`; it ships a `sitemap-config.ts` exporting `SITEMAP` (read by the site map page and the footer) and a `plan-du-site` route redirecting to `/plan-du-site?from=<board-id>`; its MongoDB `boards` record (`name_fr`, `name_en`, `homePageVisible`…) feeds the home page and the contact form; its accessibility statement relies on an audit record `tableaux_<board-id>` served by `/get-last-audit/` — ask the team for it if missing. Page titles come from `title-i18n.json` through `useTitle`. A board missing one of these is not finished, even if its pages work.
- Server route modules are explicitly mounted from `server/src/router.js`. Read `server/src/routes/boards/AGENTS.md` before changing board APIs.
- See `plugins/tableaux/reference/README.md` for the prototype architecture, component references, manifest and data-source constraints.
- The `dashboard` skill (modes `init`, `build`, `critique`, `accessibility`) and the `chart` and `dsfr` skills live in the `tableaux` plugin under `plugins/tableaux/skills/`. For DSFR UI and styling, consult `plugins/tableaux/skills/dsfr/SKILL.md`.
- See `plugins/tableaux/reference/url-parameters.md` for URL and API parameter names shared across boards.

## Runtime and commands

- Main local commands are `npm start`, `npm run build`, and `npm run build:staging` from the repository root.
- `npm run build` is the primary frontend verification command because it runs TypeScript compilation and Vite build through the workspace scripts.
- The repository currently has no package-script unit or browser test suite. API behavior is commonly checked with `.http` request files under `server/src/routes/**/api-tests/`.
- `npm -w client run lint` exists but currently depends on an ESLint 9 flat-config migration that is not yet in place in this repository. Report this status explicitly when validation is requested.

## Safety and data

- Never include credentials, production records, or confidential data in prompts, logs, or generated files. Do not create sample or fixture data for a dashboard; ask which data source to use (a repository source or a user-defined one) first.
- Authenticated data sources (MongoDB, Elasticsearch, Paysage, ODS) are read-only only. The credentials are already configured on the server, so only the exact index or collection and the data classification need developer confirmation. A new source (not in the table above) also needs its token name, never its value, confirmed. Ask the questions in `plugins/tableaux/reference/guides/data-specs.md` first, and ask about fields before coding.
- Do not create or modify MongoDB dashboard records, deployment settings, secrets, or production routes as part of prototyping without an explicit human-approved task.
- Never read or print `.env` files or expose credentials. Client-side `VITE_*` variables are included in the built bundle and must not contain secrets.

## Architecture and conventions

- Use `ChartWrapper` for Highcharts, with `useQuery` keys containing all relevant filters. Handle loading, error, and empty states explicitly; keep expected data errors on the page so users can adjust filters.
- Every data-driven block — chart, KPI card, data table, list of results — is greyed out as soon as it is being recomputed, so that a stale value is never mistaken for the current selection. Use a skeleton only for the first load. Afterwards keep the previous content (`placeholderData: keepPreviousData`) and cover it with an overlay showing a loading indicator, with `aria-busy`, for the whole recomputation: while the API call is pending (`isPlaceholderData`) and while the block is re-rendered after new data or a local control change (indicator, tab, sort), including a synchronous Highcharts redraw (apply the new value only after the overlay has been painted). Titles, comments, legends and tables describe the displayed data, not the pending one. Reference implementation: `client/src/boards/suivi-recherche/components/chart-busy/` (overlay) and `client/src/boards/suivi-recherche/hooks/use-render-transition.ts` (applies a new value only after the overlay is painted); propose moving them to `client/src/components/` when a second board needs them.
- Build every Highcharts options object with `createChartOptions(type, options)` from `client/src/components/chart-wrapper/default-options.ts` (the shared version of `european-projects`' `CreateChartOptions`): it applies the DSFR theme tokens, fonts, axes, tooltip, legend, credits and accessibility defaults. Pass only chart-specific options; do not restate those defaults or build a raw options object.
- Compute on the server, not in the browser. Filtering, aggregation, joins, ratios and success rates, rankings, sorting, top-N, period comparisons and derived geometry belong in the board's server route (MongoDB pipeline or route code, cached when the input is static), which returns chart-ready data sized to what is displayed. The client only maps that response to series, formats labels and renders. `european-projects` is the reference (e.g. `/european-projects/overview/programs-funding` returns totals and `successRateByProgram` already computed).
- **Every ratio is shown with its numerator and denominator.** A share, rate, success rate or index is never displayed alone. The route returns it as `{ valeur, numerateur, denominateur }`, summing counts before dividing (never averaging ratios); the page states the calculation in words, with units — « 18,4 % (560 lauréats / 3 039 candidatures) » — at least in the chart tooltip, and also in the accessible data table and in the detail line of a KPI card. A reference value (average, whole population) is shown the same way. When the denominator is small, the route returns a reliability flag against a threshold it defines, and the page says « peu fiable » in text (badge, tooltip, table), not by color alone. Reference: `server/src/routes/boards/suivi-recherche/routes/erc.js` and `client/src/boards/suivi-recherche/pages/financements/charts/erc-evolution/`.
- A local control (indicator, metric, tab, sort) must switch the chart instantly. Either the route returns ready-to-plot values for every option of the control, or the control is a query parameter of the route so each answer is fetched once and cached by `useQuery`. Never recompute a full dataset on each toggle; wrap any remaining client-side mapping in `useMemo` keyed on the data and the control.
- Name URL parameters as described in `plugins/tableaux/reference/url-parameters.md`: `snake_case`, the shared vocabulary for shared notions (`section` for the selected tab of a page, `paysage_id` / `ror_id` for structures, `year`, `year_min` / `year_max`, `region`, `country_code`, `language`), the same names in the page URL and the API route, no default value written to the URL, and old names rewritten so that existing links keep working.
- Follow the nearest board's i18n pattern. Provide French text and English text when the board is multilingual.
- Every board has its own server router under `server/src/routes/boards/<board-id>/`, even when it serves a user-defined public source, so that promotion replaces data access without changing the client contract.
- Keep code dedicated to the board by default. Reuse existing `server/src/commons` and `server/src/services` code, and extract domain-neutral infrastructure into them only when a second board needs it; see `plugins/tableaux/reference/README.md` ("Common or dedicated code").
- Keep shared components shared only when a second board needs them. Boards must not import from one another except through `boards/integration/charts-registry.tsx`.
- For new server routes, use the shared error classes and error middleware; use the repository logger instead of `console.log`.
- Follow neighboring file conventions for imports, extensions, formatting, and language.
- Write the simplest code that works, in the idioms of the surrounding files: one intention per function, explicit names, no trick that needs a comment to be understood. Do not introduce a parallel pattern (another state model, another data-fetching layer, another styling approach) next to the one the repository already uses.
- Before changing a shared component or module (`client/src/components/`, `client/src/layout/`, `server/src/commons`, `server/src/services`), list every usage across all boards (`grep`) and prefer a non-intrusive change — a new optional prop, an extension — over a change of existing behavior. A change to shared code is assessed at the scale of the whole application, not of the board you are working on.

## UI, DSFR and accessibility

These rules are requirements, not preferences: a change that breaks one of them is not mergeable. The detailed guidance is in `plugins/tableaux/skills/dsfr/SKILL.md`; read it before writing or changing any page, layout, component or SCSS in `client/src`.

- **The DSFR is applied strictly.** When `@dataesr/dsfr-plus` (or the DSFR) has a component for what you are building, you use it — tabs, accordions, modals, selects, form fields, badges, alerts, pagination… Never rebuild a DSFR component by hand, not even "because the DSFR JavaScript does not drive React-owned nodes": the dsfr-plus components *are* the React implementation of that behavior. If a shared component is broken or not accessible, fix it at the source (in `@dataesr/dsfr-plus` or `client/src/components/`) and say so in the pull request; do not write a local replacement in the board.
- **There is a single header and a single main navigation, identical in every board**: `client/src/layout/header` (`Header`, own `i18n.json`), always used through `client/src/layout/layout.tsx` (`Layout`: skiplinks + header + `<main id="main-content">` + footer), introduced by Victor's pull request #201. Every board layout and page is a thin wrapper around `Layout`: `items` (Accueil first, with the `home-4-line` icon), `serviceName` / `serviceTag` (title and tagline), `exploreLink` and `languageSelector` (off by default), `themeSwitch` (on by default), `extra` (header tools), `navExtra` (right side of the menu bar), `before` (content rendered in `<main>` before the page, e.g. a selection bar), `footer`. A board never writes its own header, navigation bar, `<main>`, `<SwitchTheme />` or skiplinks, nor a variant of them (different placement, styling, menu behavior or markup); a defect is fixed in `client/src/layout`, for every board at once. The same options are used everywhere: a header feature (explore link, language selector) is on for all boards or for none, not chosen board by board.
- **The skiplinks** ("liens d'évitement": Contenu principal / Menu / Pied de page, RGAA 12.7) are rendered once, by `Header`. Targets are `#main-content` (`Layout`), `#main-menu` (the nav, only when there are items) and `#footer` (`Footer`); pages must not add their own `<main>` or skiplinks.
- **The `template` board is the design reference for every board**: footer, skip links, page title, filter bar, KPI cards, section structure, in addition to the header and navigation above. A new board follows it; a board does not get its own layout or component set. A deviation is a design decision to raise with the team before coding, not a judgment call inside a pull request.
- **Board SCSS is for layout only.** A board's `styles.scss` may position elements (`display: flex | grid`, `gap`, widths, responsive breakpoints). It never defines appearance: no colors, backgrounds, borders, shadows, radii, font sizes or weights, hover/focus/active states. Appearance comes from DSFR components, `fr-*` utilities (spacing `fr-m*`/`fr-p*`, typography `fr-text--*`/`fr-h*`, surfaces `fr-background-*`, text colors `fr-text-*`) and decision tokens. Do not neutralize DSFR styles (margins, underlines, tints) to make a hand-made layout work: use the DSFR component whose layout already fits.
- **Colors are DSFR decision tokens, used for their role**: `var(--text-*)`, `var(--background-*)`, `var(--border-*)`, `var(--artwork-*)`. Never a hex value, never a primitive (`--blue-france-sun-113-625`), never a state token (`*-hover`, `*-active`) outside that state. Chart series colors come from `createChartOptions`, `useChartColor` / `client/src/utils/colors.ts` and the board's `colors.scss`, which map to the DSFR illustrative palette and handle the dark theme.
- **Accessibility is RGAA-complete, without exception.** These are public-sector applications: every page, control and chart must be usable with the keyboard alone and with a screen reader, in both themes, at 320 px width and at 200 % zoom. Semantic HTML, a `<label>` per field, unique `id`s via `useId`, visible focus (never removed), `aria-current` on navigation, `lang` matching the displayed language, one `h1` per page with no skipped levels, information never carried by color alone, `prefers-reduced-motion` respected. Every chart offers an accessible data table: `ChartWrapper` renders Highcharts' native table by default (`viewData`, with the chart title as caption); pass `renderData` only when that native table is not readable as is (series keys that are not human labels, values needing units or formatting, several axes, data the chart does not show). The Highcharts accessibility module stays enabled. Every accessibility finding is blocking — there is no "to fix later" category — and an accessibility regression is a bug, not a detail. Apply the checklist in `plugins/tableaux/skills/dashboard/reference/accessibility.md` while writing, not only when reviewing.
- DSFR JavaScript is loaded by `DSFRConfig` (`client/src/main.tsx`, from `@dataesr/dsfr-plus`) and drives the modals of the shared `Header` and `Footer` only (mobile menu, theme, language). Outside those, do not rely on DSFR JS behaviors (`data-fr-opened`, `data-fr-js-*`, `aria-controls` towards a `fr-modal` / `fr-collapse`) on React-owned nodes; use dsfr-plus components, native HTML behavior, or explicit React state.
- Do not invent DSFR markup from memory. When no dsfr-plus component exists, read `node_modules/@gouvfr/dsfr/example/component/<name>/index.html` at the installed version and reproduce its DOM and ARIA exactly.
- No inline layout styles (`style={{}}`), no invented `fr-*` classes, no `!important`.

## Git and delivery conventions

- Day-to-day work happens on `staging`; `main` is updated through deployment flow.
- Do not run `npm run deploy:*` or its pre/postdeploy scripts from agent tasks; these commands bump versions, merge branches, and push tags.
- Keep pull requests focused and call out any required human approvals (dashboard registration, backend exposure, and preview data access).

## Validation

- Available checks include `npm run build` and, when lint configuration is migrated, `npm -w client run lint`.
- No repository-wide PR validation or package-script test suite is configured. Report checks that do not exist instead of claiming they passed.
- Before a UI change is handed over: test the changed pages with the keyboard alone and with a screen reader (VoiceOver), in light and dark theme, at a mobile width, and report what was tested. No automated accessibility or style check (axe, pa11y, `eslint-plugin-jsx-a11y`, stylelint) exists yet in the repository; do not claim one ran.
- Keep pull requests focused and describe required dashboard registration, server changes, data access, and checks that remain for a human reviewer.
