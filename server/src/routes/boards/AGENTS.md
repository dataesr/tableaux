# Board API development guidance

- Board APIs are Node.js/Express routes under `server/src/routes/boards/<board-id>/`. Every board has one, including prototypes; start from `server/src/routes/boards/template/`.
- New route modules must be explicitly imported and mounted from `server/src/router.js`; adding a file alone does not activate a route.
- Follow neighboring routes for input validation, response shapes, async error handling, and MongoDB access. Use the shared error middleware and existing helpers where appropriate. Throw `BadRequestError` and the other classes from `server/src/commons/errors` (async errors are forwarded by `express-async-errors`); prefer them over `checkQuery`, which sends a 400 but does not stop the handler.
- Routes do the computation and return chart-ready data. Filter, group, join, compute ratios and rates, rank, sort and cut to top-N in the MongoDB aggregation pipeline (`$match`, `$group`, `$sort`, `$limit`, with indexes on the filtered fields) or in the route code, and return only the fields and rows the chart displays. Reference: `european-projects/routes/horizon-europe/overview/programs-funding/index.js`, which returns totals and `successRateByProgram`. Do not send raw rows for the browser to reshape.
- When a chart has a local switch (indicator, metric, tab), either return the values for every option in one response or accept the option as a validated query parameter. Precompute costly derived structures (rankings over years, cumulative values, layout geometry) on the server, and cache responses whose inputs are static fixtures or snapshots.
- Query parameters follow `plugins/tableaux/reference/url-parameters.md` and have the same names and values as the page URL parameters (`ror_id`, `paysage_id`, `year_min`, `year_max`, `region`…). Validate each one and throw `BadRequestError` for an invalid value; an absent optional parameter means its documented default (e.g. no structure identifier = national scope). When renaming a parameter, update the client and the `.http` files in the same change.
- Keep database credentials and service tokens on the server. Do not expose them to the frontend, prompts, or logs.
- Prototype routes read only the data source confirmed by the developer (a read-only preview source requires its owner's approval, datasets and access controls). Isolate data access in one place so promotion replaces it without changing the route path or response shape. Never connect an AI-generated frontend directly to MongoDB.
- Before writing a helper, search `server/src/commons`, `server/src/services`, `server/src/routes/utils.js`, and other boards. Keep dataset-specific code (pipelines, collection names, filter vocabularies, response shaping) in the board. Extract domain-neutral infrastructure (errors, validation, caching, external-API clients such as Paysage or ODS) only when a second board needs it, and propose it in the pull request instead of editing shared code silently.
- Do not add or expose a route solely on the assumption that a prototype route is private. Identify its access control, deployment exposure, and reviewer before implementation.
- Backend changes require an explicit human review by the service/data owner. Provide an `api-tests/**/*.http` request file; the repository has no package-script backend test suite or pull-request check workflow, so do not claim those checks ran.
