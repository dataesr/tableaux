# Interface DSFR dans tableaux

Le DSFR arrive par `@dataesr/dsfr-plus`, dont le JS importe `@gouvfr/dsfr/dist/dsfr.min.css` et `utility/utility.min.css` (`@gouvfr/dsfr` **1.11.0**, installé en peer) ; son propre `style.css` n'ajoute que des icônes. Pour vérifier qu'un token ou une classe existe : `grep` dans ces fichiers. Les comportements viennent de React, sauf les modales du `Header` et du `Footer` partagés, pilotées par le JS du DSFR (§ JS DSFR).

## 0. Principes

### Le DSFR s'applique strictement

- **Si dsfr-plus (ou le DSFR) a un composant pour ce que vous construisez, vous l'utilisez.** Ce n'est pas un premier choix parmi d'autres : c'est la règle. Cela vaut pour les onglets, accordéons, modales, sélecteurs, champs de formulaire, badges, alertes, pagination…
- **On ne réécrit jamais un composant DSFR à la main**, même « parce que le JS du DSFR n'agit pas sur les nœuds React » : les composants dsfr-plus _sont_ l'implémentation React de ces comportements. Un accordéon en `useState` + SCSS, un onglet en `div`, c'est non.
- **Le header et la navigation principale sont ceux de l'application, identiques dans tous les boards** : `client/src/layout/header` (`Header`), toujours via `client/src/layout/layout.tsx` (`Layout` : liens d'évitement + header + `<main id="main-content">` + footer), introduits par la PR #201 de Victor. Le layout d'un board est un simple wrapper de `Layout` qui passe `items` (« Accueil » en premier, `icon: "home-4-line"`), `serviceTag` / `serviceName`, `footer`, et au besoin `before` (barre de sélection rendue dans `<main>`), `extra` (outils du header), `navExtra` (droite de la barre de menu), `exploreLink`, `languageSelector`, `themeSwitch`. Un board n'écrit jamais son propre header, sa propre barre de navigation, son `<main>`, ses liens d'évitement ni `<SwitchTheme />`, ni une variante (placement, style, comportement du menu, balisage différents) ; un défaut se corrige dans `client/src/layout`, pour tous les boards à la fois. Une option du header (lien « Explorer », sélecteur de langue) est activée pour tous les boards ou pour aucun, pas au cas par cas.
  Evidemment, la tagling "Si c'était pas super ça s'appellerait juste data" doit disparaitre.
- **Un composant partagé défaillant se corrige à la source** — dans `@dataesr/dsfr-plus` ou dans `client/src/components/` — et on le dit dans la PR. On n'écrit pas un remplaçant local dans le board.
- **Le board `template` est la référence de design de tous les boards** : footer, liens d'évitement, titre de page, barre de filtres, cartes de chiffres clés, structure des sections — en plus du header et de la navigation ci-dessus. Un board ne se dote pas de son propre layout ni de son propre jeu de composants. S'écarter du template est une décision de design à soumettre à l'équipe avant de coder.
- **Le SCSS d'un board ne sert qu'à la disposition** (§4). L'apparence — couleurs, bordures, ombres, typographie, états — vient du DSFR, jamais d'un `styles.scss`.
- **L'accessibilité est complète (RGAA), sans exception** (§5). Tout constat est bloquant ; une régression d'accessibilité est un bug.

### Deux sources priment sur la mémoire

Ne jamais écrire du balisage `fr-*` de mémoire : ce sera subtilement faux (classe inventée, ARIA manquante, structure d'une autre version).

1. **Les types de dsfr-plus** : `node_modules/@dataesr/dsfr-plus/dist/components/<Composant>/*.d.ts`. Si TS refuse une prop, elle n'existe pas — ne pas caster.
2. **`node_modules/@gouvfr/dsfr/example/component/<nom>/index.html`** : le DOM et l'ARIA canoniques, à la version installée. À lire avant d'écrire à la main le moindre balisage `fr-*`.

### JS DSFR

`DSFRConfig` (`main.tsx`, fourni par dsfr-plus) charge et démarre le JS du DSFR. Il pilote **uniquement** les modales du `Header` et du `Footer` partagés (`data-fr-opened` / `aria-controls` : menu mobile, thème, langue), qui reproduisent le balisage canonique du DSFR. Partout ailleurs, le JS DSFR agit sur des nœuds que React possède : ne pas compter dessus, et ne pas écrire de `data-fr-opened`, `data-fr-js-*` ou d'`aria-controls` vers une `fr-modal` / `fr-collapse` dans un board. Ordre des comportements : composant dsfr-plus → élément natif (`<details>`, `<dialog>`, `<select>`) → état React (`useState` + `aria-expanded` + classe/rendu conditionnel). Pour refermer une modale DSFR après une navigation, voir `concealModal` dans `layout/header`.

S'il reste des accordéons ou sélecteurs faits main dans du code existant : ne pas les recopier dans du nouveau code.

### Où chercher — dans cet ordre, et on s'arrête au premier qui couvre le besoin

1. **Composants dsfr-plus** (obligatoires dès qu'ils existent) : `Container`/`Row`/`Col`, `Title`/`Text`, `Button`, `Badge`, `Tag`, `Alert`, `Notice`, `Accordion`, `Modal` (+ `ModalTitle`, `ModalContent`, `ModalFooter`), `Tabs`, `SegmentedControl`, `Select`, `Autocomplete`, `Checkbox`, `Radio`, `Toggle`, `Input`, `SearchBar`, `Breadcrumb`, `SideMenu`, `Header`/`Nav`, `Pagination`, `Stepper`, `Spinner`, `Toast`…
2. **Composants partagés du repo** : `client/src/components/` (`chart-wrapper`, `charts-skeletons`, `select`, `item-filter`, `callout`, `copy-button`…). Les chercher avant d'écrire. Certains ont des défauts d'accessibilité connus (`searchable-select` : options en `div onClick`, `id` fixe ; `breadcrumb` : `fr-collapse` sans état) : **on les corrige** (à la source, en vérifiant tous leurs usages dans l'app, par une modification non intrusive), on n'écrit pas un équivalent local. Note : `Autocomplete` de dsfr-plus est une barre de recherche (formulaire + bouton, saisie libre, popover), pas un sélecteur ; pour choisir dans une liste, `Select` de dsfr-plus, et si une liste longue l'exige, le composant partagé `select` du repo une fois corrigé.
3. **Utilitaires `fr-*`** pour l'espacement, la typo, les couleurs (§1).
4. **Balisage `fr-*` brut** — uniquement pour un motif DSFR que dsfr-plus ne couvre pas encore, en reproduisant exactement le DOM et l'ARIA de l'exemple canonique, et en proposant son ajout à dsfr-plus.

Il n'y a pas de cinquième niveau : un besoin que rien ne couvre est une question à poser à l'équipe, pas un composant à inventer en SCSS.

**Proscrits dans du nouveau code** : `style={{}}` pour la mise en page, classes `fr-*` inventées, couleurs hex en dur (ça casse le thème sombre, piloté par `data-fr-theme`), tokens primitifs (`--blue-france-sun-113-625`) ou tokens d'état (`*-hover`, `*-active`) hors de leur état, JS DSFR, `!important`, SCSS d'apparence (§4), composant DSFR réécrit à la main.

## 1. Les utilitaires DSFR utiles

**Espacement** — `v` = 0.25rem, `w` = 0.5rem (`2w` = 1rem) : `fr-m{t|b|l|r|x|y}-{n}{v|w}`, `fr-p…` (ex. `fr-mb-2w`, `fr-px-3v`, `fr-mt-0`). `fr-mb-0` est le cheval de trait (§3.1).

**Typographie** — `fr-text--xs|sm|md|lg|lead`, `fr-text--bold|regular|light` ; `fr-h1`…`fr-h6` utilisables sur n'importe quelle balise (`<p className="fr-h4">` pour une valeur chiffrée). Le corps fait 1rem : réserver `fr-text--sm` aux mentions et notes, pas au « texte un peu plus petit ». Couleurs : `fr-text-mention--grey`, `fr-text-title--grey`, `fr-text-default--{error|success|warning|info}`.

**Icônes** — `fr-icon-<nom>` sur un `<span aria-hidden="true">`, taille `fr-icon--sm|md|lg` ; ou la prop `icon` des composants dsfr-plus, **sans préfixe** : `Button` génère `fr-icon-${icon}` (`icon="download-line"`). Le `Callout` du repo (`components/callout.tsx`), lui, prend la classe complète (`icon="fr-icon-information-line"`). Vérifier que l'icône existe par `grep` dans les CSS (§ intro). Un bouton à icône seule porte un `aria-label` (ou `title`), pas un texte masqué à la main.

**Divers** — `fr-sr-only` (masqué visuellement, lu par les lecteurs d'écran), `fr-hidden` / `fr-unhidden-{bp}`, `fr-raw-link` (§3.2), `fr-background-alt--grey`, `fr-background-contrast--grey` pour les surfaces.

## 2. Composition

- **Gouttières plutôt que marges entre frères** : le parent (flex/grid avec `gap`, ou `Row gutters`) porte l'espace ; un enfant ne porte pas de marge extérieure. Les marges sont pour le flux de la prose.
- **Un rythme par surface** : `2w` par défaut, `1w` pour une liste serrée, `3w` pour un jeu de cartes. On varie entre groupes, pas à l'intérieur.
- **L'espace fait la hiérarchie** : plus d'espace au-dessus d'un titre de section qu'en dessous.
- **Gauche/droite** (titre + actions, libellé + valeur) : d'abord `Row` avec `fr-col`/`fr-col-auto` ; sinon un flex `justify-content: space-between` — jamais de `float`, de positionnement absolu ni de grille à 2 colonnes.
- **La prose** (méthodologie, FAQ, mentions) garde les marges natives du DSFR : ne pas tout emballer dans des conteneurs flex.
- Les tableaux de bord méritent la largeur : graphiques et filtres ne sont pas une colonne de lecture.
- Ne pas tout mettre en cartes, ne jamais imbriquer une carte dans une carte : à l'intérieur, la hiérarchie vient de la typo et de l'espacement.
- Une rangée de filtres : une seule taille de champ, une seule famille visuelle. Les critères (« quel sous-ensemble ») sont des champs ; les contrôles d'affichage (« comment afficher » : export, vue) sont des boutons.

## 3. Cas CSS inévitables — symptôme, cause, remède

Cette section n'est pas une licence pour surcharger le DSFR. Avant d'appliquer un « remède », vérifier qu'un composant ou un utilitaire DSFR ne règle pas le problème par construction (un `fr-mb-0`, un `Row gutters`, le bon composant de formulaire). Les cas ci-dessous sont les seuls où une règle SCSS locale est admise, et elle reste limitée à la disposition : neutraliser une marge, un padding ou une largeur — jamais changer une couleur, une bordure, une ombre ou un état.

1. **Marges de `fr-text--*` / `fr-h*` / `<p>` dans le chrome** — un libellé décale une barre, une carte a un vide sous chaque ligne. Chaque classe de texte porte un `margin-bottom` (`--text-spacing` / `--title-spacing`, 1.5rem), et un conteneur flex bloquifie ses enfants. Remède : `fr-mb-0` sur chaque élément texte d'une carte ou d'une barre ; dans une barre dense, `--text-spacing: 0; --title-spacing: 0;` une fois sur la barre. Pas dans la prose.
2. **Tout `a[href]` est stylé** — soulignement en `background-image` (pleine largeur dans un flex en `stretch`), flèche des liens externes, couleur imposée. Remède : `fr-raw-link` sur le sous-arbre, ou dans le SCSS du composant `background-image: none; --underline-idle-width: 0; --underline-hover-width: 0;` ; aligner les liens sur `flex-start`.
3. **`<hr>` a un padding** (`padding: var(--text-spacing)`). Remède : `padding: 0` sur tout séparateur maison.
4. **Champs désalignés dans une ligne de filtres** — `.fr-input-group:not(:last-child)` / `.fr-select-group` ont une marge basse, `fr-input` une marge haute après le label. Remède : neutraliser ces marges sur les enfants directs de la rangée avec une spécificité supérieure (classe de la rangée + classe du groupe), et masquer les `.fr-messages-group` vides.
5. **Teinte de survol sur tout `button`** — le DSFR teinte `button:not(:disabled)` via `--hover-tint` / `--active-tint`. C'est le comportement DSFR : on le garde. Si la teinte semble gênante, c'est que l'élément n'est pas le bon composant (`Button variant="text"`, `Tag`, lien) — changer de composant, pas la variable.
6. **Anneaux de focus différents** — un `<input>` montre l'anneau au clic, un bouton seulement au clavier (`:focus-visible`). C'est voulu : ne pas « corriger ».
7. **Case à cocher décalée** — le DSFR dessine la case en `label::before` à `left: -1.5rem`, relatif au `margin-left` du label. Ne compacter que les marges de bloc, jamais ce `margin-left`.
8. **Les défauts navigateur sont remis à zéro** (listes, `<dialog>`, titres) : ajouter l'espacement par les utilitaires, ne pas supposer qu'il existe.
9. **Un seul `::before`** — les icônes `fr-icon-*` dessinent dans `::before`, la surcouche de `fr-enlarge-link` aussi : un lien couvrant qui porte une icône perd sa surcouche (le clic ne marche que sur le texte). Mettre l'icône à droite (`::after`) ou dans un `<span>` séparé.
10. **Focus dans un popup maison** — un anneau extérieur peut être rogné par les bords. Préserver l'indicateur de focus ; si un style spécifique est indispensable, utiliser un token DSFR vérifié et une règle localisée au popup plutôt qu'une couleur codée en dur.

## 4. Composants propres à un board

- **Composer d'abord** : la plupart des « composants sur mesure » sont des composants dsfr-plus + utilitaires typo/espacement.
- **Le SCSS d'un board ne fait que disposer** : `display: flex | grid`, `gap`, `flex-wrap`, largeurs, points de rupture, et les quelques neutralisations du §3. Il ne définit **jamais** l'apparence : pas de `color`, `background`, `border`, `box-shadow`, `border-radius`, `font-size`, `font-weight`, pas de `:hover` / `:focus` / `[aria-current]` stylés. L'apparence vient du composant dsfr-plus et des utilitaires (`fr-background-alt--grey`, `fr-text-mention--grey`, `fr-text--sm`…). Un `styles.scss` qui dessine une barre, une carte, un onglet ou un état actif, c'est un composant DSFR réécrit : à remplacer par le composant.
- **Quand un token est inévitable** (disposition d'un graphique, surface via `createChartOptions`), uniquement une variable de **décision** utilisée pour son rôle (`var(--text-mention-grey)`, `var(--background-alt-grey)`, `var(--border-default-grey)`…) — jamais d'hex, jamais de primitive, jamais un token d'état hors de son état (`--background-default-grey-hover` n'est pas une couleur de fond). Pour les graphiques, le thème Highcharts vient de `createChartOptions` (`client/src/components/chart-wrapper/default-options.ts`) et les couleurs de séries passent par `useChartColor`, `client/src/utils/colors.ts` et les `colors.scss` des boards, qui s'appuient sur la palette illustrative du DSFR et gèrent le thème sombre.
- **Sémantique** : un vrai `<button type="button">` ou `<a href>` reçoit focus, teintes et clavier du DSFR ; un `div onClick` jamais. On surcharge les opinions DSFR non voulues (§3), on ne dégrade pas l'élément.
- **SCSS** : colocalisé (`styles.scss` à côté du composant), classes préfixées par le board, en reprenant le préfixe déjà en place (ex. `ep-…` pour european-projects, `outcomes-…` pour devenir-etudiants, `atlas-…`) ; ne jamais créer de classe `fr-*`, propriétés logiques (`margin-inline`, `padding-block`), pas d'`!important`.
- **Échelle d'extraction** : 1 usage = local au board ; besoin réel dans un 2ᵉ board = remonter dans `client/src/components/`. Jamais par anticipation, jamais par copier-coller entre boards. Un board n'importe pas les fichiers d'un autre board (seul `boards/integration/charts-registry.tsx` le fait, par construction).
- **Modifier un composant partagé** (`client/src/components/`, `client/src/layout/`, dsfr-plus) : lister d'abord tous ses usages dans l'app (`grep`), privilégier une prop optionnelle ou une extension à un changement de comportement, et annoncer l'impact dans la PR. Le changement s'évalue à l'échelle de toute l'application, pas du board en cours.
- **Le code le plus simple qui marche**, dans les idiomes des fichiers voisins : une intention par fonction, des noms explicites, pas d'astuce qui demande un commentaire. Pas de pattern parallèle (autre gestion d'état, autre couche d'accès aux données, autre façon de styler) à côté de celui du repo.

## 5. Construire et valider

- **Ordre** : structure avec de vraies données (libellés français réels, volumes réels) → mise en page → typo et couleurs → états interactifs → états limites → responsive.
- **États de chaque élément interactif** : normal, survol, focus (dessin distinct du survol), actif, désactivé, chargement, erreur, vide.
  - Chargement : `DefaultSkeleton` (ou les autres `charts-skeletons`) au premier chargement seulement ; `Spinner` réservé aux actions.
  - Recalcul (filtre, indicateur, onglet, tri) : tout bloc qui dépend des données — graphique, carte de chiffres clés, tableau, liste — reste affiché mais **grisé** (voile semi-transparent sur `var(--background-default-grey)`, indicateur de chargement, `aria-busy`, texte en `role="status"`) pendant l'appel API et pendant le nouveau rendu. Référence : `boards/suivi-recherche/components/chart-busy/` et `hooks/use-render-transition.ts`.
  - Vide : un message qui explique quoi faire (changer de filtre, d'année…), pas un graphique vide.
  - Erreur attendue (filtre sans résultat, 4xx) : affichée sur place (`Alert`, `Notice`) sans démonter la page ni les filtres.
- **États limites** : 0 élément, 1 élément, des centaines, des libellés très longs (noms d'établissements), années sans données.
- **Accessibilité : RGAA complet, sans exception.** Ce sont des applications publiques ; tout constat est bloquant, il n'y a pas de catégorie « à corriger plus tard ». En écrivant : HTML sémantique (`button`, `a`, `nav`, `main`, listes), `id` uniques via `useId`, chaque champ a un `<label>` visible relié, ordre de titres cohérent (un seul `h1` par page, pas de niveau sauté), focus visible jamais supprimé, `aria-current="page"` sur la navigation, `lang` conforme à la langue affichée, information jamais portée par la seule couleur, contrastes via les tokens, `prefers-reduced-motion` respecté, lisible à 320 px et à 200 % de zoom. Tout graphique offre un tableau de données accessible : `ChartWrapper` affiche par défaut le tableau natif de Highcharts (`viewData`, légende = titre du graphique) ; `renderData` ne sert que lorsque ce tableau natif n'est pas lisible tel quel (clés qui ne sont pas des libellés, valeurs à formater, plusieurs axes, données que le graphique n'affiche pas). Le module d'accessibilité Highcharts reste activé. Dérouler la liste de `plugins/tableaux/skills/dashboard/reference/accessibility.md` pendant l'écriture, pas seulement en relecture.
- **Validation humaine** : on ne voit pas le rendu. Lancer les vérifications indiquées dans le `AGENTS.md` racine, relire contre le §0 (composant obligatoire, SCSS de disposition seulement) et le §5, puis donner à l'utilisateur **la route à ouvrir** (`http://localhost:5173/<board>/<page>`) et une **liste de vérification** : thème clair/sombre, mobile (320 px), zoom 200 %, navigation au clavier seul, lecteur d'écran (VoiceOver), états vides et limites à déclencher. Aucune vérification automatisée d'accessibilité ou de style n'existe dans le repo : ne pas prétendre en avoir lancé une.
